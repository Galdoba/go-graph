# Design

## Context

The rule set in `pkg/link` answers for one pair from what the two members carry, and the build records what a declaration refers to as a use attribute of the node that owns it (`pkg/graph/build.go:332`, `recordUses` walks the whole declaration: parameters, results, body, and the receiver). Only a structure is read as a source today. `referentObj` (`pkg/graph/build.go:497`) builds an identifier from any object, without checking that the object is a node, so references can name entities the model records as attributes instead of nodes. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**

- One rule that reads the references a node carries, so a declaration connects to the package-level entity it names anywhere in itself.
- A recorded reference names a node or carries its value, as the node model already states.
- The receiver is read from the receiver property, not from a reference.

**Non-Goals:**

- No new attribute kind and no positional marker for where a reference came from, so an argument link and a body link are the same fact.
- No distinction in the record between incoming and outgoing references: a pair is counted in the outgoing direction from the node that owns the declaration.
- No link labels in the note body, no cross-package graph, no change to identity or note naming.

## Decisions

**The rule reads use attributes and no semantic value.** Only the kind that records an entity a declaration refers to is read; method attributes record the method set and alias attributes record a name, so they keep naming no relation. Alternative considered: filter the target by semantic type — rejected, because a node is by definition a package-level declaration, which already excludes local entities, and the requested targets are nodes of any kind. Alternative considered: a new attribute kind recorded only from the parameter list — rejected, because it cannot be told apart from a use without changing the shape of an attribute, and the relation wanted here is wider than the parameter list.

**Node membership is enforced at record time, not inside the rule.** A rule reads only the pair, so it cannot verify that a reference names a node that exists in the collection; the node model already requires that a reference point at a node, so the build should record the reference only when the object it names is a node and carry the referent as the value otherwise. Alternative considered: a rule that answers only when the target is a known node — rejected as a lookup outside the pair.

**The receiver is not recorded as a use.** The method node already carries the receiver as its receiver property and its parent, which the existing method rule reads. Alternative considered: record the receiver as its own attribute kind so the rule can skip it — rejected as redundant data. Skipping it at record time is also the only place the exclusion can live, because a rule cannot know which part of a declaration a use came from.

**The new rule is appended at the end of the fixed order.** It never answers that a pair cannot be decided, because it reads no semantic value, so the rule named for an undecided pair does not change. Only the size of the rule set changes. Alternative considered: inserting it before the satisfaction rule — no outcome differs, and appending keeps the documented order as the order the relations were decided.

## Risks / Trade-offs

- [References that name non-nodes are removed from the record, so a consumer reading the reference of a field, a parameter, a local or a type parameter reads nothing] → the attribute still carries the name and the value, and the node model already states that a name the model does not record as a node carries its referent as the value.
- [The answered set grows on real code: an entry point that names many package-level entities becomes a hub] → the answered set for the test ground is asserted as a whole, so the growth is visible in the tests rather than inferred.
- [A method that uses a name equal to a package-level declaration answers for the wrong entity until the record is fixed] → fixed by the node-membership rule: `r.Read()` through an interface names a method spec, so no reference is recorded, and the package-level function of the same name is not reached.
- [The test ground output changes, which reaches the note files] → `pkg/vault` writes the related section from `link.Pairs`, so `examples/Thing.md` and the vault tests are regenerated with the answered set.

## Migration Plan

No stored data changes: answers are read from the records at the moment they are asked, and nothing is kept between builds. Existing note files are regenerated by the same command that produced them, so the change lands as regenerated output rather than a migration. Rollback is a revert of the rule and the recording change together, because the answered set depends on both.

## Open Questions

- Whether a note should label an argument link differently from a body link. The fact is one pair, so no label is recorded, and the question can be answered when the graph is built.
- Whether references to entities in packages that are not part of the same set of records should appear once a cross-package graph exists. That belongs to the deferred graph layer.
- Whether a reference names the node of a method declared in another package. The node-ness of a foreign entity is read from the scope that declares it, which holds no method, so a method of another package carries no reference today. The change that handles foreign methods owns that case.
